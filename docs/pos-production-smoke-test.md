# Hasim Cashier — Production Smoke Test (جهاز Android حقيقي)

تاريخ: 2026-09-02  
الهدف: التحقق اليدوي أن Standalone POS يعمل **بدون إنترنت** وأن البيع لا يعتمد على الطباعة أو Laravel.

جهّز: جهاز Android، بناء `apps/hasim_cashier`، طابعة شبكة اختيارية، ماسح HID إن وُجد.  
سجّل لكل سيناريو: Pass / Fail + ملاحظة + لقطة إن فشل.

---

## Scenario 1 — Fresh install → Standalone setup → login

1. امسح بيانات التطبيق أو ثبّت جديداً.
2. افتح التطبيق (بدون إنترنت إن أمكن).
3. اختر «كاشير محلي مستقل» / إعداد المتجر.
4. أدخل اسم المتجر، مدير، مستخدم، PIN من 4 أرقام على الأقل.
5. بعد الحفظ يجب أن تصل لشاشة PIN أو الكاشير دون طلب خادم.
6. أغلق التطبيق تماماً (Force stop) ثم افتحه: يجب أن يطلب PIN ولا يدخل تلقائياً.
7. PIN خاطئ يُرفض. PIN صحيح يدخل.

**يفشل إذا:** ظهر خطأ API، أو دخل بدون PIN بعد إعادة الفتح، أو `workspace` بدا كأنه «1» في واجهة التشخيص دون UUID للمتجر.

---

## Scenario 2 — Create product → sale → cash payment → invoice

1. من الإدارة المحلية أنشئ صنفاً: اسم، سعر، باركود، مخزون معلوم (مثلاً 10).
2. افتح وردية من الإعدادات بنقد افتتاحي معروف (مثلاً 100).
3. أضف الصنف للسلة، ادفع نقداً بمبلغ أكبر من الإجمالي، أكّد الباقي.
4. يجب ظهور رقم فاتورة `INV-000001` (أو بادئة المتجر).
5. المخزون ينقص بالكمية المباعة.
6. الفاتورة تظهر في قائمة الفواتير بنفس الإجمالي.

**يفشل إذا:** فشل الدفع بسبب الشبكة، أو الرقم تكرر، أو المخزون لم ينقص، أو بقي في السلة بعد النجاح.

---

## Scenario 3 — Kill app → reopen → verify data

1. بعد Scenario 2 أضف صنفاً للسلة دون دفع.
2. Force stop.
3. أعد الفتح وسجّل PIN: السلة يجب أن تعود (مسودة SQLite).
4. غيّر الكمية، Force stop، أعد الفتح: الكمية المعدّلة تبقى.
5. أكمل الدفع، ثم فور ظهور النجاح Force stop إن أمكن قبل الطباعة.
6. أعد الفتح: فاتورة واحدة فقط، لا بيع مكرر، السلة فارغة.

**يفشل إذا:** اختفت المسودة، أو ظهرت فاتورتان لنفس العملية، أو فُقدت المبيعات السابقة.

---

## Scenario 4 — Return sale → verify stock

1. من الطلبات/الفواتير سجّل مرتجعاً لكمية أقل من المباعة.
2. المخزون يزيد بنفس الكمية.
3. إجمالي الفاتورة الأصلية لا يتغير.
4. التقرير اليومي: `invoices_total` كما هو، `return_amount` يزيد، `net_sales` ينقص.
5. حاول إرجاع كمية أكبر من المتبقية: يجب الرفض.
6. كرّر المرتجع لنفس الكمية المستنفدة: يجب الرفض.

**يفشل إذا:** تعذّر المرتجع (خصوصاً إن ظهر خطأ تحويل رقم)، أو تغيّرت الفاتورة الأصلية، أو زاد المخزون مرتين.

---

## Scenario 5 — Open shift → sales → cash out → close shift

1. وردية مفتوحة من Scenario 2 أو أغلق وافتح من جديد.
2. نفّذ بيعاً نقدياً وآخر إن أمكن.
3. سجّل صرف نقدي (cash out) إن وُجد في الواجهة.
4. أغلق الوردية بنقد فعلي مختلف عن المتوقع.
5. تحقق: Expected = افتتاح + مبيعات نقدية − مرتجع − صرف؛ Difference = Actual − Expected.
6. حاول إغلاق نفس الوردية ثانية: يُرفض.
7. حاول فتح ورديتين في نفس المتجر: يجب أن تبقى واحدة مفتوحة.
8. مستخدم كاشير (إن أُنشئ) لا يغلق الوردية ولا يعمل مرتجعاً ولا يعدّل الكتالوج ولا يعمل Backup.

**يفشل إذا:** أمكن فتح ورديتين، أو البيع بدون وردية، أو معادلة الصندوق خاطئة.

---

## Scenario 6 — Disconnect internet completely → repeat sales

1. فعّل وضع الطيران.
2. كرّر بيعاً نقدياً ومرتجعاً جزئياً وتقرير اليوم.
3. لا رسائل «تعذر الاتصال» تمنع البيع.
4. لا قائمة انتظار مزامنة إلزامية لإتمام البيع.

**يفشل إذا:** تجمّدت شاشة أو استُدعي الخادم كشرط للبيع.

---

## Scenario 7 — Printer unavailable → sale still succeeds

1. أزل الطابعة أو ضع IP خاطئ.
2. أتم بيعاً.
3. البيع والفاتورة ينجحان؛ رسالة الطباعة تفشل منفصلة.
4. من الفاتورة أعد الطباعة بعد إعادة توصيل الطابعة (أو تأكد أن الزر موجود حتى مع الفشل).

**يفشل إذا:** اعتُبر البيع فاشلاً بسبب الطابعة.

---

## Scenario 8 — Backup → reinstall/restore → verify

1. أنشئ: أصناف، عميل إن وُجد، عدة فواتير، مرتجع، وردية (مفتوحة أو مغلقة).
2. صدّر Backup من الإعدادات (صلاحية مدير).
3. سجّل: عدد الفواتير، مجموع المبيعات، مخزون صنف، رقم آخر فاتورة، فرق الوردية إن أُغلقت.
4. امسح بيانات التطبيق أو استعد فوقها بعد التأكيد.
5. قارن نفس الأرقام والتقارير.

**يفشل إذا:** اختفت المرتجعات/الحركات/المستخدمون، أو تغيّر المجموع، أو رُفض الملف بسبب checksum بعد تعديل يدوي (هذا النجاح للـ checksum).

حالات إضافية: Backup لمتجر فارغ؛ Backup بعد ~50 صنفاً على الأقل.

---

## Scenario 9 — Barcode scanner

1. امسح باركود صنف موجود (لوحة مفاتيح HID): يُضاف للسلة بالـ `local_id` لا `serverId`.
2. باركود مجهول: لا يُضاف صنف فارغ؛ رسالة واضحة.
3. امسح نفس الباركود مرات: تزيد الكمية أو تُضاف أسطر حسب تصميم السلة (وثّق السلوك الفعلي).
4. امسح والسلة مفتوحة بعد إعادة تشغيل التطبيق: البحث محلي.

**يفشل إذا:** اعتمد البحث على `serverId` أو فشل بلا شبكة.

---

## Scenario 10 — Large catalog

1. استورد/أنشئ أكبر كتالوج متاح يدوياً (مئات إلى آلاف إن أمكن).
2. افتح الكتالوج، ابحث بالاسم، امسح باركود، أتم بيعاً، افتح تقرير اليوم.
3. راقب التأخير: بحث > ثانية على جهاز متوسط = سجّل Fail أداء.

**يفشل إذا:** تجمّد التطبيق أو تحميل كل الفواتير في الذاكرة جعل التقرير غير قابل للاستخدام.

---

## قائمة تحقق سريعة قبل الإصدار الداخلي

- [ ] لا دخول Standalone بدون PIN بعد إعادة التشغيل
- [ ] لا بيع بدون وردية
- [ ] لا فاتورة مكررة عند الضغط مرتين على دفع
- [ ] البيع ينجح والطابعة مفصولة
- [ ] المرتجع لا يغيّر الفاتورة الأصلية
- [ ] Backup/Restore يطابق المجاميع
- [ ] وضع الطيران لا يوقف الكاشير
- [ ] الكاشير لا يستعيد/لا يعدّل المخزون يدوياً/لا يغلق وردية/لا يعمل Backup
